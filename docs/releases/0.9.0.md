# 0.9.0 — Timed performance observation

## Product scope

Adds **Анализ → Сеанс производительности…**, continuing issue #26 after the 0.8.0 event/process review. The window opens idle. Select a duration of 30/60/120/300/600 seconds and an interval of 1/2/5 seconds (default **120 seconds / 2 seconds**), start observation, reproduce the symptom and add timestamped notes with **Отметить симптом**. The session stops at its configured end or via **Остановить и сохранить замеры**. That button retains observations in memory; saving files requires the separate export button.

The live chart switches between CPU, physical-memory use, aggregate physical-disk busy percentage and disk queue. The table retains every completed sample, actual receipt time, elapsed session offset, collection duration and warnings. Notes are limited to 100 per session / 160 characters per note. Marker time is the click time, not a recovered historical onset of a freeze. A complete machine/GUI freeze can delay both sampling and marker entry.

Charts split at unavailable values and long gaps (greater than 1.75 times the selected interval). Missing values are never drawn as zero. Live statistics show median, nearest-rank P95, maximum and valid/total samples; the full report also includes minimum and number of samples at/above the displayed reference thresholds. These counts are not time fractions or measured duration of overload. Reference levels are CPU 85%, RAM used 85%, disk busy 80% and queue 2; queue alone is not a diagnosed bottleneck.

Clipboard and local HTML/JSON export include the entire session, all four metrics, symptom markers, limits, outcome and missing-data explanations. The HTML contains four static SVG charts and the full sample table, with user text encoded and no external script/assets. Exports use a unique directory and do not overwrite prior reports. Starting another session replaces the in-memory result; export a session before starting another one to retain it.

## Measurement semantics

- CPU: change in GetSystemTimes kernel+user minus idle, normalized by kernel+user. Kernel includes idle. Missing baseline, reset or inconsistent counters remain unavailable. The result is an interval average, not Task Manager's frequency-scaled processor utility. In this iteration, systems without exactly one confirmed active processor group report CPU unavailable rather than displaying a single group's value as whole-machine CPU.
- RAM: GlobalMemoryStatusEx physical total/available, not application working-set sum or commit charge. The native structure is 64 bytes.
- Disk: local WMI `Win32_PerfFormattedData_PerfDisk_PhysicalDisk`, `_Total`, `100 - PercentIdleTime` and `CurrentDiskQueueLength`. This is provider-wide aggregate activity/instantaneous queue, not the Windows system volume alone. Idle is validated in 0–100 before conversion; missing/invalid measurements stay unavailable. Queue is not a percentage and is not clamped to 100.
- CPU/RAM/disk are read sequentially, not atomically; WMI has its own refresh cadence. Every plotted point is labelled with completion time. Source collection time is visible, and this utility can itself add load.

Timing uses a monotonic clock, bounded slots and one synchronous provider read at a time on a background worker. Elapsed slots are counted as missed rather than caught up in bursts. A due final sample permits up to 100 ms of scheduling lateness; its actual timestamp is preserved, not rewritten to the planned time. A system call already in progress can complete after the configured duration. The disk provider has requested 2-second operation timeouts, but neither these nor cancellation guarantee immediate OS/provider termination. Stopping retains completed samples and explicitly omits an incomplete sample. One shared session gate remains held until real provider completion, including when the window is closed.

Outcome and completeness are separate. `Completed` means the observation loop completed, not that every metric was available or the workstation is healthy. No original Health Score/Coverage, threshold, collector, process, network setting or remediation behavior is changed. No stress load, driver, new package, third-party executable, service, unattended collector or automatic upload is added. Arbitrary EXE location/name and UAC behavior remain as in 0.5.2.

## Required Windows 11 pilot

Use standard-user Windows 11, reproduce an actual application delay, add notes, stop early, export, start another session and close/reopen during collection. Check 100/150/200% DPI, long notes, unavailable/slow WMI, protected environments, sleep/resume, system-clock changes and long provider overruns. Compare tools only with matching metric definitions and intervals. No accuracy benchmark, per-process attribution or causal diagnosis is claimed. Hosted Windows Server integration and bitmap rendering do not replace visual/real-workload acceptance. Interactive UAC and real repairs remain separate tests; the EXE is not Authenticode-signed.
