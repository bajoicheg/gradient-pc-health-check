# 0.7.0 — Explicit resource diagnostics

## Delivered scope

Next approved item from #26 after 0.6.0: user-initiated name resolution and TCP connectivity to a single selected port, in the same portable EXE. Open **Анализ → Проверить доступность ресурса (DNS/TCP)…**, enter a hostname/IP and port, tick the explicit outbound-request consent, and run. No destination is prefilled, contacted on opening or saved to a persistent history. Editing the target/port or completing a run clears consent.

Each session records normalized target, limits, start/finish timestamps, resolved addresses, per-stage outcomes/elapsed time/socket code, local source IP on successful TCP and warnings. Repeat attempts remain distinct; different endpoints are not represented as a repair comparison. Clipboard/HTML/JSON include current and previous attempts. Exports create unique directories and HTML-encode all variable text.

## Measurement boundaries

- DNS is Windows/.NET system name resolution; DNS cache, hosts, suffix search and platform resolution policy may contribute. It is not proof of a specific DNS server response.
- A literal IPv4/IPv6 address bypasses name resolution. IDN names become ASCII/punycode. Input is one name/address, not a URL, credential-bearing string, shell command, CIDR or range. Legacy abbreviated/hex/octal IPv4 notation is rejected.
- TCP connects once to each selected resolved address and the selected port, sends no application bytes and closes. No TLS, HTTP, authentication, file-share login or application transaction is performed. Port presets are labels, not protocol tests.
- Direct sockets use OS routing/VPN. HTTP proxy/PAC settings are not followed; in a proxy-only environment a direct TCP failure does not show that the browser is broken. No DNS, proxy, VPN, routing or firewall setting is changed.
- Default limits are 5 s for resolution, 3 s per TCP address and eight addresses; the UI permits 1–10 s per TCP attempt. Unusable/multicast addresses are skipped, duplicate answers are not probed twice, and truncation is explicit. Ordering follows the resolver; this is not browser Happy Eyeballs behavior.
- Mixed success and untested addresses cannot yield a full Connected result. Cancelled sessions retain completed facts and identify the incomplete attempt. Timeout/refusal/unreachability are observations, not automatic attribution to a firewall or server fault.
- Elapsed time is name-resolution/connection time, not ICMP latency or throughput. A successful TCP handshake is not a health verdict for the workstation or application.

## Architecture / preserved scope

ResourceTargetParser, ResourceProbeService and the injectable network interface separate deterministic behavior from real OS I/O. SystemResourceProbeNetwork uses the .NET 8 Dns and TcpClient APIs. The form has no background/automatic probe. Models and reports are separate from the original Health Score/diagnostic schema. No package, worker allow-list, elevation, existing collector or workflow-permission change.

Temp preview and startup review from 0.6.0, and arbitrary-name/path elevation from 0.5.2 remain. Process-linked connection inventory, incident Event Log filtering, monitoring graphs, hardware sensors and general folder analysis are later backlog items, not included here.

## Required Windows 11 pilot

Verify a known permitted internal service by its FQDN and IP, with/without the intended VPN, on IPv4/IPv6 and with a proxy-only path where applicable. Try approved refused/timeout cases, cancel during DNS/TCP, change endpoint, export successive attempts, and confirm no repair is applied. Check 100/150/200% DPI and keyboard navigation. Tests do not disable security controls or probe third-party targets. Interactive UAC/DISM/SFC remain outside the new integration test.

The PE is not Authenticode-signed. OS policy may block DNS or sockets. Network providers may have cancellation behavior below the task API that this utility cannot prove stopped immediately.
