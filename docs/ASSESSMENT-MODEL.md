# Health assessment model

Документ фиксирует семантику Health Score, общего Status и Coverage, чтобы после E2E пороги можно было калибровать осознанно, а не менять «по ощущениям».

## 1. Три разных понятия

### Health Score: 0–100

Score — эвристический приоритет проблем, которые **фактически обнаружены**. Он начинается со 100 и уменьшается на penalty диагностических findings.

Score не является вероятностью исправности и не должен интерпретироваться как SLA/SLO или «процент здоровья» ПК.

### Status: OK / WARN / CRIT

Status — уровень внимания инженера Service Desk.

Правило 0.3.3:

- если существует хотя бы один finding `CRIT` → общий Status = `CRIT`;
- иначе, если существует хотя бы один `WARN` или Score < 85 → `WARN`;
- иначе → `OK`.

То есть высокий Score больше не может скрыть отдельный критический сигнал.

### Coverage: 0–100

Coverage отвечает на другой вопрос: **насколько полно удалось собрать телеметрию, необходимую для первичной диагностики**.

Отсутствие сигнала не уменьшает Health Score — иначе недостаток данных выглядел бы как доказанная неисправность. Вместо этого при недостаточном coverage создаётся отдельный finding `WARN / Данные`, и общий Status перестаёт быть `OK`.

## 2. Coverage weights

| Сигнал | Вес |
|---|---:|
| CPU | 15 |
| RAM | 15 |
| Системный диск / свободное место | 20 |
| Disk queue | 10 |
| Health физического накопителя | 15 |
| Windows OS + build | 10 |
| TOP процессов | 10 |
| Антивирус / EDR | 5 |
| **Итого** | **100** |

Границы:

- `HIGH`: 85–100;
- `MEDIUM`: 65–84;
- `LOW`: 0–64.

До накопления статистики E2E это рабочая эвристика, а не окончательная модель.

## 3. Текущие performance/storage thresholds

| Сигнал | WARN | CRIT |
|---|---:|---:|
| CPU | >= 85% | >= 95% |
| RAM available | <= 15% | <= 8% |
| System disk free | <= 15% **или** <= 20 GB | <= 8% **или** <= 10 GB |
| Disk queue | >= 2 | >= 5 |
| Uptime | >= 14 дней | >= 30 дней* |

\* Uptime >= 30 дней в текущей логике создаёт усиленный `WARN`, а не `CRIT`: большой uptime сам по себе не доказывает критическую неисправность.

Нагрузка CPU и диска с 0.3.2 берётся как медиана короткой серии, а не единичный snapshot.

## 4. Event Log: повторяемость важнее raw count

Абсолютное число `Critical + Error` за 24 часа недостаточно для штрафа.

Текущие условия:

- WARN: total >= 20 **и** один Provider/Event ID повторился >= 5 раз;
- CRIT: total >= 100 **и** один Provider/Event ID повторился >= 20 раз.

Цель — не превращать обычный шум Application/System log в false positive. После E2E следует отдельно проанализировать наиболее частые Provider/Event ID на реальных медленных ПК и на контрольной группе.

## 5. Penalties

Основные текущие penalty:

| Finding | Penalty |
|---|---:|
| CPU WARN / CRIT | 7 / 15 |
| RAM WARN / CRIT | 7 / 15 |
| System disk free WARN / CRIT | 7 / 15 |
| Disk queue WARN / CRIT | 5 / 12 |
| Physical disk unhealthy | 20 |
| Uptime >=14 / >=30 дней | 3 / 5 |
| Pending reboot | 5 |
| Repeated Event Log WARN / CRIT | 4 / 10 |
| Startup items >=20 | 3 |
| Missing telemetry / incomplete coverage | **0** |

Coverage warning intentionally has penalty 0: uncertainty and confirmed degradation — разные сущности.

## 6. Как калибровать после E2E

Для каждого реального обращения «ПК тормозит» сохранять:

1. исходный Score/Status/Coverage;
2. основные findings;
3. субъективный симптом пользователя;
4. подтверждённую RCA инженером;
5. выполненное действие;
6. Score/Status после действия;
7. факт: проблема устранена / не устранена / причина не подтверждена.

После первых 20–30 кейсов уже можно искать:

- thresholds, которые систематически дают false positive;
- сигналы, которые часто присутствуют на healthy/control ПК;
- findings с высокой связью с подтверждённой RCA;
- случаи, где Coverage HIGH, но приложение систематически пропускает известную причину.

До такой выборки не следует усложнять Score псевдоточной математикой или ML-моделью.

## 7. Инварианты модели

Эти правила должны сохраняться при развитии:

- `нет данных` ≠ `здоров`;
- `CRIT finding` не может давать общий `OK`;
- одна мгновенная нагрузка не должна считаться устойчивой проблемой;
- большое число разнородных Event Log ошибок не равно RCA;
- remediation success code не равен доказательству устранения причины — нужна повторная диагностика;
- Health Score не должен автоматически разрешать разрушительные действия.
